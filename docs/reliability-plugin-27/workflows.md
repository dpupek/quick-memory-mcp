# User workflows

| Workflow | User and motivation | Steps and observable outcome | Delivery |
| --- | --- | --- | --- |
| W1. Assign a project role | An administrator needs predictable access for operators, developers and readers. | Assign the tier and project override. Exercise an allowed and a denied action through both clients. Verify the same decision, a useful tool error, and unchanged data after denial. | [#28](https://github.com/dpupek/quick-memory-mcp/issues/28), [#26](https://github.com/dpupek/quick-memory-mcp/issues/26) |
| W2. Upgrade or recover the service | An operator needs a supported runtime and a recoverable store. | Back up a disposable installation, upgrade binaries, reconnect Codex, write a fixture, restart and restore. Check service identity, prior config, fixture contents, search and audit output. Rehearse rollback. | [#29](https://github.com/dpupek/quick-memory-mcp/issues/29), [#30](https://github.com/dpupek/quick-memory-mcp/issues/30) |
| W3. Resume a case | A SysOps operator returning to an incident needs the last verified state and next action. A Campus developer needs the same for a software case. | Resolve the workspace project once. Search the case field and legacy text. Show a short handoff with date, verification, unresolved work, source ID and next action. Fetch a full entry only when needed. If there is no match, say so. | [#31](https://github.com/dpupek/quick-memory-mcp/issues/31), [#32](https://github.com/dpupek/quick-memory-mcp/issues/32) |
| W4. Find a decision | A Campus developer or SysOps operator needs the reason for an earlier choice. | Search in the selected scope. Return dated matches with project or shared origin. Open the best source and distinguish the recorded decision from later updates. Identify conflicting or superseded records when the evidence supports it. | [#31](https://github.com/dpupek/quick-memory-mcp/issues/31), [#12](https://github.com/dpupek/quick-memory-mcp/issues/12), [#13](https://github.com/dpupek/quick-memory-mcp/issues/13), [#32](https://github.com/dpupek/quick-memory-mcp/issues/32) |
| W5. Save a handoff | A departing user wants the next person to pick up at the right point. | On explicit request, find the existing handoff, verify its case and project, then update by ID or create once. Include the change, verification, source and next action. Repeat the save and verify one logical handoff. On failure surface retry status. | [#28](https://github.com/dpupek/quick-memory-mcp/issues/28), [#30](https://github.com/dpupek/quick-memory-mcp/issues/30), [#32](https://github.com/dpupek/quick-memory-mcp/issues/32) |
| W6. Evaluate the pilot | The two cohort leads need evidence for rollout. | Select private known-answer fixtures, capture the current workflow, run the same prompts with the plugin, score each cohort, and record an expand, revise or stop decision. Use aggregate results for public reporting. | [#25](https://github.com/dpupek/quick-memory-mcp/issues/25), [#31](https://github.com/dpupek/quick-memory-mcp/issues/31), [#32](https://github.com/dpupek/quick-memory-mcp/issues/32) |

When a workspace mapping is ambiguous, ask the user to select among authorized matches before search or save. When a user lacks write access, keep the handoff available in the chat and report the denied save.
